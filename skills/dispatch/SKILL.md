Главная сессия выносит задачу в свой workspace herdr, чтобы её ход,
вопросы и долгие команды не занимали контекст главной сессии. Навык
выполняется в главной сессии, а не форком: записку составляют из того,
что знает только она, — цели, сделанного, решений пользователя. Сам
запуск — сценарий `dispatch.sh`, одна команда с проверкой каждого шага.

## Когда выносить

Задача подпадает под вынос, если выполнено хотя бы одно:

- занимает ресурс реестра занятости (`busy.resources`), внешний узел или
  стенд проекта;
- работает с узлом Jenkins (`jenkins.nodes`): настройка, разбор, ожидание
  `jwait.sh`, короткие прогоны по разрешению записки; долгое на Jenkins —
  `~/.claude/CLAUDE.md`, «Ветви, pull request'ы и конвейер»;
- содержит прогон, сборку или ожидание дольше 10 минут;
- правит больше одного репозитория (репозиторий проекта и сабмодули
  считаются по отдельности);
- идёт через изменение OpenSpec.

Остальное — субагентом главной сессии или навыками `/duty:*`.

Задача субагенту или в workspace ставится только с запиской по форме
`${CLAUDE_PLUGIN_ROOT}/reference/brief-template.md`, крупная — только этим
навыком. Справку по документам для строки «Справка» готовит `/duty:recall <тема>`;
при сборке записки из `--goal` строка задаётся ключом `--recall`, раздел
«Приоритеты» — ключом `--priorities`. Форму проверяют
ворота: `dispatch.sh` и хук плагина (README плагина, «Ворота постановки»).

## Вход

Переданные аргументы вызова (подставлены при запуске, пустая строка —
аргументов нет): «$ARGUMENTS».

Допустимые значения: `<имя-задачи> <модель> [текст задачи, путь к записке или --resume]`.

- Имя — `[a-z][a-z0-9_-]{0,31}`, говорящее: оно же имя агента herdr и сессии Claude и имя каталога
  задачи; символ workspace (из набора `symbols.tasks` конфигурации, вне репозитория —
  `symbols.outside`; не занятый открытыми workspace; `symbols.main` — символ
  главной сессии, задачам не выдаётся) выбирает `dispatch.sh` и сообщает
  herdr токеном `symbol`; набора нет — символ выдаёт herdr дочернему workspace
  (`[ui.workspace_symbols]` каталога родителя, токены в `herdr workspace get`),
  herdr не дал — запасной `scripts/symbols.txt`. Цвет заголовка назначает herdr
  по правилу `ui.workspace_symbols.color_rule` (токен `color` в `workspace get`);
  без форка herdr, не знающего правила, плагин считает цвет сам по тому же правилу
  (`scripts/rule-color.py`) и шлёт токеном `color`; метка workspace и первой
  вкладки — «<символ> имя · модель», вкладок команд — «▸ имя прогона»
  (подписывает `tab-run.sh`, без символа и модели: панель агентов группирует
  вкладки по workspace); в любой вкладке herdr, где работает агент, указана
  модель. `list`, `stalled`, `symbol` и `close`
  как имя не годятся.
- Модель — по лесенке из раздела «Модель» ниже.
- Третий аргумент — путь к готовой записке, текст цели или `--resume`:
  продолжение задачи с этим именем в её прежнем каталоге (`state.md`
  есть, живого агента нет — `dispatch.sh stalled`).

## Модель

Признаки проверяются до запуска; подходит самая дешёвая ступень, у которой
выполнены все признаки; один признак следующей ступени поднимает задачу
на неё.

- `haiku` — команды уже написаны, решений по ходу нет, итог проверяется
  одной командой: пробы, перечни, запуск готовых сценариев.
- `sonnet` — есть образец или спецификация, по которой делать; один
  репозиторий; готовность проверяется командой (тесты,
  `openspec validate --strict`, линтеры); новых решений о поведении
  не требуется: правка по правилу, документ по готовому решению, прогон
  и разбор вывода, настройка через REST.
- `opus` — хотя бы один признак: причина падения неизвестна и воспроизведения
  нет; проектируется новое поведение, схема данных или протокол; код без
  образца в репозитории; конфликт двух правил или спецификаций; слияние
  с конфликтами; задача затрагивает несколько репозиториев.
- `fable` — только когда это слово стоит в аргументе: главная сессия
  передаёт его после согласия пользователя, предложив Fable с обоснованием.
  Признаки, при которых его предлагать: Opus дважды вернул отчёт с ошибкой
  или противоречием; решение меняет правила проекта или записи решений;
  набор из многих спецификаций или репозиториев, принимаемый вместе; ошибка
  дорога и необратима (выкат, конвейер, перенос в `master`).

Ревью и его уровень по модели исполнителя — правило проекта
(`docs.review` конфигурации); раздел «Замечания ревью» в `report.md` — по
`reference/report.md`, п. 4.

Правила движения:

- Вверх — по сигналу из отчёта исполнителя: «не решено», второй провал
  проверки, противоречие отчёта фактам, больше трёх вопросов пользователю за задачу,
  воспроизведённая ломающая находка ревью, которую исполнитель
  не исправил, если принять с тикетом нельзя. Воспроизведённые
  ломающие находки ревью у исполнителей одной ступени в двух задачах
  подряд — следующая задача такого рода ставится на ступень выше.
  Задача перезапускается на ступень выше с тем же `brief.md`; новый
  исполнитель начинает с `state.md` и `report.md` предыдущего (порядок
  продолжения — `agents/worker.md`, «Порядок работы», п. 1).
- Вниз — через записку: `brief.md` и критерии приёмки пишет модель
  на ступень выше исполнителя, исполняет дешёвая.

## Шаги

1. Составить записку, если третий аргумент — не путь к готовой и не
   `--resume`: файл в scratchpad по
   `${CLAUDE_PLUGIN_ROOT}/reference/brief-template.md`: разделы и обязательные
   среди них — там; порядок постановки — `~/.claude/CLAUDE.md`, «Постановка
   задачи». Раздел «Приоритеты» — порядок предпочтений между вариантами
   выполнения, по которому агент решает обратимые развилки без вопроса
   (`agents/worker.md`, п. 5); у задачи без развилок — «развилок нет —
   <причина>». Разрешения на записи во внешних системах — явно, иначе их нет;
   push ветвей-копий и pull request — `~/.claude/CLAUDE.md`, «Ветви, pull
   request'ы и конвейер»: pull request записка не разрешает.
2. Если для задачи действуют свои запреты и решения сверх общих
   (`${CLAUDE_PLUGIN_ROOT}/reference/worker-rules.md` и `.duty/worker-rules.md`
   проекта), — файл с ними
   в scratchpad, по пункту на строку.
3. Запустить:

   ```sh
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/dispatch.sh" <имя> <модель> \
     --brief <записка> [--rules <файл>] [--main <имя главной сессии>]
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/dispatch.sh" <имя> <модель> --resume [--main <имя>]
   ```

   Вместо `--brief` для короткой задачи — `--goal '<цель>' --done '<критерий
   с командой в обратных кавычках>' --stop '<условие остановки>' --read
   '<прочитанное при постановке>' --recall '<путь итога /duty:recall | не нужна —
   причина>' --priorities '<порядок предпочтений | развилок нет — причина>'`:
   записка соберётся из шаблона. `--main` —
   имя главной сессии из `ListAgents`,
   если оно не совпадает с именем её агента herdr. Корень
   проекта — `${CLAUDE_PROJECT_DIR}` (у агента задачи — `DUTY_PROJECT`),
   каталог задачи — `<results>/<имя>/`, где `<results>` — каталог результатов
   из конфигурации (`python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/duty_config.py" get paths.results`).

   Готово, когда сценарий вышел с кодом 0 и напечатал `workspace=`,
   `symbol=`, `pane=`, `status=working`, `status=blocked` или `status=idle`
   (приглашение ушло в транскрипт, а первый ход был коротким). Код 1 — причина
   в последней строке; созданный workspace остаётся для осмотра. Отказ ворот —
   тот же код с именами разделов, каталог задачи и workspace не создаются.
   Предупреждение «herdr не подтвердил готовность агента» не отказ: агент занят
   приглашением с первой секунды, сценарий сам закрепил за ним имя.
4. Записку и правила из scratchpad удалить: копии лежат в каталоге
   задачи.

## Дальше

- Новые запреты и решения пользователя по задаче главная сессия
  дописывает в раздел «Переданные» файла `rules.md` задачи; агент
  перечитывает его перед каждым внешним действием.
- Вопросы агент задачи задаёт пользователю сам, в своём workspace
  (`AskUserQuestion`, порядок — `agents/worker.md`, п. 5); главная сессия
  их не видит и на них не отвечает. Решения шире задачи и развилки,
  решённые по приоритетам, приходят в отчёте («Решения за пользователем»):
  решение шире задачи главная сессия при приёме записывает `/duty:decision`.
- Просроченные ожидания (`⚠ просрочено +N мин` в `dispatch.sh list`,
  `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/signals.py" list --waits`, `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/busy.py" list`; хук печатает их при старте):
  задача ждёт дольше срока своей строки «Ожидания». Агент сам шлёт
  сообщение с шапкой (`agents/worker.md`, п. 8а); если его нет —
  спросить агента (`SendMessage`), не продлевать молча. Причина — зависшая
  операция, сигнал, который не придёт, упавший узел — разбирается по
  правилу починки набора (`~/.claude/CLAUDE.md`); ожидание без срока
  (`⚠ без срока`) — исправить строку в `state.md` задачи.
- Задача без живого агента с незавершённым `state.md` (хук печатает
  `dispatch.sh stalled`) продолжается `dispatch.sh <имя> <модель>
  --resume`; завершённую задачу отметить строкой `Шаг: завершено`
  в её `state.md`.
- Остаток лимитов главной сессии (контекста или токенов) меньше 2 % —
  сессия может оборваться: дописать в раздел «Переданные» файла
  `rules.md` каждой открытой задачи распоряжение слать промежуточные
  итоги сообщением после каждого шага (правило — `agents/worker.md`,
  «Порядок работы», п. 9). Полученные итоги вносятся в проектный снимок передачи работы
  ссылками (ветвь, хеши, путь к `state.md`), чтобы новая сессия
  продолжила без повторной работы. Без распоряжения исполнитель
  ведёт только `state.md`.
- Итог приходит сообщением `SendMessage` (три строки и путь
  к `report.md`) и уведомлением herdr. Закрытие workspace — `agents/worker.md`,
  «Завершение», п. 11. Решение пользователя оставить его открытым главная
  сессия записывает в «Переданные» файла `rules.md` словами «по решению
  пользователя»; сама такого указания не даёт: сохранение контекста агента,
  ожидание набора или слияния причиной не считаются, продолжение работы
  ставится новой задачей с запиской по отчёту и ветвям в origin. Оставшийся открытым
  workspace закрывается `dispatch.sh close <имя>` после проверки отчёта.
- Открытые workspace задач — `dispatch.sh list`.
- Зависимость между задачами называется в `brief.md` именем сигнала
  (раздел «Зависимости»). Получив от агента «жду сигнал <имя>: <что
  означает>», главная сессия дописывает в раздел «Переданные» файла
  `rules.md` задачи-источника, если та открыта, «по окончании дать сигнал
  <имя>», а получив итог источника, сама даёт сигнал
  (`python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/signals.py" signal <имя> '<текст>' --keep`), если источник не дал.
  `task-done-<имя>` даёт исполнитель, на случай его сбоя — `dispatch.sh
  close` (после передачи не даётся). Сигнал между проектами записка
  называет вместе с проектом («Ждёт: `<сигнал>` (проект `<имя>`)»), а
  исполнитель ждёт его с `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/signals.py" wait <сигнал> --project <имя>` (имя —
  каталог `~/.local/state/duty/<имя>` или абсолютный путь корня); главная
  сессия сигналы между проектами не дублирует. Открытые ожидания печатает хук
  при старте (`python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/signals.py" list --waits`).
